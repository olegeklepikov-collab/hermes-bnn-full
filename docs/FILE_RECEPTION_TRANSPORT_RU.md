# Доставка назначенных файлов: исходник, JSON и защитная обёртка

Пара выпуска: Memory 2.0.0-dev.55 / Intake 0.14.15.

## Подтверждённый отказ

Сообщение `assigned_file_reception_source_changed` возникало при чтении назначенного JSON через `memory_files`. Проверка реального сбойного входа показала: все три исходных файла сохраняли назначенные SHA-256. Две доставленные страницы отличались четырьмя символами каждая: подчёркивания в `untrusted_tool_result` заменялись дефисами.

Это точное стандартное преобразование защитной обёртки Hermes. Оно не является изменением файла. Контроль приёма сравнивал изменённый текст с исходным и ошибочно объявлял смену версии источника. Поэтому уменьшение задачи или повтор чтения не устраняли причину.

Отказ длиной около 15 секунд относился к фоновому содержательному разбору. В сохранённой истории основной ответ был завершён перед запуском этого исполнителя. Фоновая рекомендация не является обязательным внешним человеческим ревью и не должна подменять состояние основного ответа.

## Различаемые состояния

| Состояние | Основание | Реакция |
|---|---|---|
| Файл действительно изменился | Текущий SHA-256 не равен назначенному | Зависимое чтение останавливается; требуется проверить новую версию и назначение |
| JSON доставлен без потери данных | После декодирования значения и ключи совпадают | Приём учитывается по исходным диапазонам |
| Сохранённая прежняя проекция | Отличия в точности равны известному штатному преобразованию | Проекция указывается явно, сохраняются оба хеша |
| Иное искажение доставки | Ни исходник, ни разрешённая проекция не совпадают | `assigned_file_reception_payload_changed`; исходник не объявляется изменённым |
| Прочитана только часть | Нет непрерывного покрытия до правильного EOF | Полное чтение не засчитывается |
| Источник позже сменился или доступ отозван | Текущая версия или действующие права больше не подходят | Прежнее чтение не даёт допуска к новой версии |

## Исправление передачи

Защитная граница сохраняется. В допустимом JSON токен `untrusted_tool_result` кодируется через Unicode-последовательности для подчёркиваний. В передаваемой строке отсутствует буквальный закрывающий разделитель, но декодирование JSON возвращает исходные значения и имена полей.

Это обычное представление тех же данных средствами JSON. Оно не создаёт новых полномочий. Для обычного текста и текста за JSON-префиксом остаётся прежняя нейтрализация разделителей. Учитываются дописанное штатное уведомление о постраничной неполноте, вложенные JSON-строки и мультимодальные текстовые части.

Защитный код не доверяет объявлению «уже обёрнуто»: такой признак мог бы подставить сам источник. Настоящая внешняя граница создаётся штатным кодом заново.

## Совместимость сохранённой истории

Старые сообщения не переписываются. Если принятая страница отличается от исходного диапазона в точности по прежнему алгоритму нейтрализации, сохраняется `delivery_projection=native_untrusted_delimiter_legacy_v1`.

Квитанция различает:

- `source_sha256`: версию полного исходного файла;
- `source_fragment_sha256`: исходный диапазон;
- `fragment_sha256`: фактически доставленный декодированный фрагмент;
- `delivery_projection`: способ представления;
- `request_sha256`: физический запрос, в котором фрагмент был подан модели;
- `call_id`, `offset`, `end`, `eof`: происхождение и диапазон.

Штатная текущая передача JSON даёт проекцию `identity`: декодированный текст полностью совпадает с источником. Полное покрытие диапазонов и точность декодированного текста указываются отдельно. Повторное точное чтение может подтвердить точность всей версии, даже если раньше встречалась прежняя проекция.

Старая квитанция без нового поля читается как прежняя точная передача: старый контроллер засчитывал только точное совпадение. Новая схема базы для этого не создаётся.

## Работа на длинных входах

В одной проверке физического запроса каждый встретившийся файл читается и хешируется один раз. SHA-256 всего запроса вычисляется один раз. Между запросами такой кэш не сохраняется: последующее изменение источника обнаруживается заново.

Это устраняет повторное чтение целого файла и сериализацию всего запроса для каждой исторической страницы. Постраничность и обязательная проверка версии сохраняются. Нет нового фонового надзирателя, отдельного сервиса, повторного модельного запуска или автоматического обхода отказа.

## Сообщение об отказе

Для ошибки версии или целостности доставки больше не предлагается «меньшая задача». Указывается проверка назначенной версии и сохранённой доставки перед продолжением. Это не разрешение повторить неизвестное внешнее действие.

## Проверки

Проверяются обычный и смешанный регистр разделителя, имена JSON-полей, вложенные строки, Unicode, переносы строк, страницы с разрывом токена, штатное уведомление о неполноте и закрывающий разделитель после JSON. Произвольное повреждение и настоящая смена файла отклоняются.

Регрессия использует настоящий конструктор сообщений инструментов Hermes, настоящий Store и назначенные ресурсы. Отдельно проверяется сохранённый реальный сбойный вход без вызова модели и без записи новых квитанций. Это не выдаётся за новое исследование или повтор исходной задачи.

Окончательные доказательства включают полный нативный набор на установленном выпуске и ограниченный настоящий модельный сценарий с несколькими страницами. Само наличие файла, извлечение текста и получение модельного ответа не равны содержательному пониманию.

## Границы изменений

Не изменяются исходные материалы пользователя, границы ролей, правила назначения, ограничения внешних действий или учёт расходов. Действительно изменившийся источник требует новой согласованной версии. Неизвестные результаты старых операций не обнуляются. Продолжение сохраняет прежнюю сессию и состояние; исходное исследование автоматически не повторяется.

# Разработка и выпуск Hermes BNN

## Области

`product/` содержит точные программные исходники платформы. `locks/` закрепляет полный нейтральный программный снимок зависимостей и происхождение исходников. Программы не копируются из работающего агента при каждой сборке. Исходная основа 01.11.2026 импортирована из ранее проверенной обезличенной поставки. Это зафиксированный начальный снимок зависимостей, не доказательство независимой пересборки каждого стороннего компонента.

## Условия хоста

Первый поддержанный профиль: нативная macOS arm64, квалифицированная ОС 26.5.1 и включённая исходная R 4.6.1. Подписанные источники поставщиков сохраняются. Нет Docker, WSL или автоматического повышения прав. Другой Mac не испытан. Тестовая и разрабатываемая установки имеют собственные HOME, HERMES_HOME, состояние, идентичность, Beads, Dolt и порты; исходные учётные данные не наследуются.

## Один рабочий цикл

1. Рабочая ветка задачи и критерии в Beads.
2. Исправление в product/ и воспроизведение в tests/.
3. Быстрые проверки: `python3 -B -m unittest discover -s tests/release_engineering -v`.
4. Зафиксировать согласованные исходники, испытания и закрепления.
5. Сборка: `python3 -B packaging/release_cli.py build --version ВЕРСИЯ`. Она отвергает незафиксированные изменения, проверяет полный снимок зависимостей и создаёт цельный архив.
6. Проверка подписи и архива: `python3 -B packaging/release_cli.py verify КАТАЛОГ`.
7. Установка именно из архива: `python3 -B packaging/release_cli.py qualify КАТАЛОГ --environment test`.
8. Проверить оставшиеся критерии RELEASE_ACCEPTANCE.json и сохранить сведения с точным хешем. Пропуск не считается успехом.
9. Допускается тот же программный комплект. Продвижение не пересобирает его. Рабочую установку меняют только отдельной предусмотренной процедурой с разрешением владельца, резервом и проверкой миграций.

## Подпись

Манифест RELEASE.json подписывается SSH Ed25519, пространство имён bnn-release-v1. Закрытый ключ хранится вне Git в .operator/keys с правами 0600. Проверка использует доверенный trust/allowed_signers из исходного репозитория, а не произвольный ключ из проверяемого архива. При новой установке доверенный открытый ключ закрепляют отдельно. Подпись доказывает происхождение байтов, не смысловую корректность агента. Резерв закрытого ключа выполняется оператором в закрытом резерве, не в открытом выпуске.

## Полнота и обновления

Каждый новый номер имеет полный установочный архив. Разбиение на части допускается как транспорт одного выпуска. Исторические исправления пользователь вручную не накладывает. Текущая команда qualify не обновляет существующую пользовательскую базу: для неё требуются отдельные проверенные миграции и процедура обновления. Нельзя выдавать чистую установку за проверку обновления или восстановления.

## Публикация и CI

Главный источник: закрытый hermes-bnn-full-private. Публичный hermes-bnn-full и самостоятельные пакеты Intake являются производными экспортами. В GitHub Actions выполняются только автономные проверки; здесь нет рабочих ключей или постоянного исполнителя на Mac владельца. Нативная квалификация выполняется локально. Автоматическое развёртывание в prod отсутствует.

## Состояние и откат

Программы и данные имеют разные жизненные циклы. Не откатывать пользовательские данные при обычной смене программы. Совместимость схем и обратимость миграции проверяются на отдельной копии. Предыдущие архивы не удаляются. Отложенные работы сохраняют задания, историю и учёт ресурсов; истёкшее поколение GSD не продлевается обновлением программы.

## Сбережение места и метаданные macOS

Команда qualify проверяет подпись и весь архив потоково, сверяя каждый объект с программным деревом. Для нативной установки использует проверенный клон APFS, чтобы не записывать повторно 13 ГБ. Это проверка полного содержимого архива и настоящая установка отдельного экземпляра; независимая пересборка зависимостей не заявлена.

Исполняемые экземпляры размещаются вне облачных каталогов. Из новой копии Zotero удаляются только служебные FinderInfo/ResourceFork, после чего проверяется исходная подпись. Карантин не отключается, приложение не переподписывается, исходный дистрибутив не меняется.

Локальные пути задаются в .operator/resources.json вне Git. Ключ environment_roots может явно указывать разрешённые корни development и test. Источник подписанных программ остаётся одним и тем же. status показывает отдельные квитанции установки и указывает, что старый рабочий экземпляр ещё не переведён на эту схему.

## Автоматический допуск

Команда `admit КАТАЛОГ --evidence ДОКАЗАТЕЛЬСТВО.json ...` принимает подписанные свидетельства, проверяет подписи, контрольные суммы файлов-свидетелей, принадлежность точному архиву и все обязательные критерии из RELEASE_ACCEPTANCE.json. Отсутствующий исполнитель, фиктивный модельный прогон и противоречивые результаты не допускают выпуск. Код завершения 3 означает открытые обязательные проверки, а не сбой установки. При выполнении всех критериев приёмка завершается без обязательного внешнего человеческого ревью. Разрешение на изменение prod этим не выдаётся.

## Сохранение выбранных сред

Повторный qualify создаёт отдельную установку и записывает её в _qualified_candidates. Уже выбранные development/test и их память, Beads и вход не подменяются. Первый экземпляр пустой роли может быть выбран автоматически. Переключение существующей роли выполняется отдельно после нужных проверок и сохранения её данных. Квалификация чистой установки не является миграцией действующей среды.

## Собственная сборка Intake

При изменении Intake обновите исходники и явно квалифицированные native-compatibility.json, затем соберите wheel без сети через packaging/build_intake.py --python /путь/к/доверенному/venv/bin/python --check-reproducible. Инструмент использует версию из locks, сохраняет SOURCE_DATE_EPOCH и сверяет две сборки; не переутверждает совместимость автоматически. Точные члены wheel и совпадение с исходниками проверяются перед общим архивом. Старые записи проверок не переносятся на новый состав.

Нейтральный абсолютный корень запечатанных runtime-контрактов /opt/hermes-bnn-distribution не создаётся на машине. При установке он сопоставляется с корнем только собственного экземпляра через действующий строгий договор path_relocations. Относительный маркер в этих контрактах запрещён предсборочной проверкой.

## Подготовка нового места разработки

1. Клонируйте главный источник в development/source.
2. Создайте закрытый development/.operator с правами 0700. Скопируйте environments/resources.example.json в ../.operator/resources.json и замените все /ABSOLUTE на согласованные собственные пути. runtime_cache должен указывать на неизменённое программное дерево проверенного нейтрального полного выпуска.
3. Создайте собственный ключ Ed25519 ../.operator/keys/release_ed25519; закрытый ключ сохраняйте вне Git. Настройте доступ к нему для подписи и внесите свой открытый ключ в trust/allowed_signers с именем bnn-release. Не заменяйте проверку происхождения чужого архива доверием к случайному ключу из самого архива.
4. Выполните автономные проверки, сборку с новым номером и qualify --environment test. Внешний вход нового TEST выполняется отдельно через его Hermes/bin/hermes auth add openai-codex --no-browser. Рабочие ключи не наследуются.
5. Реальный цикл: python3 -B packaging/check_live_roundtrip.py /путь/к/кандидату. Он допускает только квалифицированный TEST точного архива, требует настоящего входа, запускает настоящего исполнителя и проверяет чтение продукта родителем. Незавершённый прежний запуск не повторяет. Исходные журналы остаются вне Git.
6. Для полного набора Intake используйте tools/run_native_tests.py в product/Intake с HERMES_INTAKE_NATIVE_ROOT квалифицированного экземпляра. Не задавайте короткий общий срок: индивидуальные исполнители сохраняют свои ограничения. При остановке результаты нельзя объявлять полным успехом; дополнение допускается только по точным именам недостающих случаев при неизменных входах и зависимостях.

Первый профиль поддерживает нативную macOS arm64 указанного квалифицированного выпуска; проверка другого физического Mac не заявлена. Привязки экземпляра и ключи в пример не входят.

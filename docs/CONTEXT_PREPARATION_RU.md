# Подготовка текущего хода без гонки с наблюдающим обработчиком

## Дефект и изменение

В прежней сборке `Host.before_turn` собирал обязательный контекст внутри `pre_llm_call`. Этот наблюдающий обработчик Hermes пропускает после 30 секунд, оставляя его поток работать. Модельный путь затем получал `current_turn_context_not_ready`; допуск мог появиться уже после отказа. Такое позднее состояние `ready` не является обработанным запросом.

Intake 0.14.8 добавляет явный адаптер `context_preparation.py` к неизменённой Memory 2.0.0-dev.48 и закреплённому Hermes. Он применяется к общему Host, независимо от режима Intake, UDR/Foundation и GSD. Подписанные программы поставщиков не изменяются.

1. `pre_llm_call` быстро сохраняет точный вход, его якоря и идентификатор хода. Не ищет материалы, не вызывает модели, внешние службы и Beads.
2. До обработки запроса адаптер синхронно выполняет прежний `before_turn` на основном пути подготовки запроса. Поэтому стандартный пропуск наблюдающего обработчика не отбрасывает обязательную сборку.
3. Прежний Admission подписывает контекст. Исходные проверки профиля, роли, текущих версий, точного входа, обязательных зависимостей и целостности сохраняются.
4. Основной `llm_execution` вызывает тот же адаптированный `host.request`. Отказ подготовки останавливает исполнение и не обходится пропуском необязательного преобразователя запроса.
5. Дальнейшие обращения той же попытки используют уже подготовленный вход; тяжёлая начальная подготовка не повторяется автоматически. Изменения данных внутри хода обновляются прежним механизмом подписанного контекста.

Подготовка внешнего запроса сохраняет основной, рабочий, процедурный, личностный и Intake-контекст через прежнюю композицию. Подготовка вспомогательных обращений остаётся в собственном назначенном пути. Прав на самостоятельные внешние действия, повтор неизвестных исходов или сброс расходов адаптер не даёт.

## Сохранение сеанса

Новый сеанс и новая задача не создаются. Не выполняются `/new`, удаление истории, перепись прежнего ответа, возврат старой базы или повтор последнего пользовательского действия. После обновления новое сообщение может продолжать тот же Telegram-сеанс и прежнюю рабочую привязку. Неподготовленный прошлый запрос не считается выполненным: пользователь при необходимости повторяет его после восстановления.

## Отказы и наблюдение

Изменение текста уже сохранённого входа того же хода отклоняется. Перекрывающий новый ход во время подготовки отклоняется, не подменяя вход работающего. При отказе зависимого компонента сохраняется безопасный код причины, повтор того же хода не запускает подготовку заново. Для нового хода требуется собственный вход и собственный допуск.

`context_preparation_timeout_seconds` по умолчанию 180 секунд относится только к подготовке одного входа. Это не общий бюджет задачи. Он проверяется после возврата сборки: превышение аннулирует только её точный допуск, модель не вызывается. Адаптер не заявляет принудительное прерывание произвольного зависшего Python-кода; зависимые операции сохраняют собственные технические тайм-ауты. Увеличение этого значения не заменяет диагностику медленного этапа.

Журнал `bnn.context_preparation` содержит хеш идентификатора хода, фазу `assemble_and_admit`, исход и длительность. Вход, документы и секреты не выводятся. Общее время подготовки не выдаётся за длительность каждой внутренней операции. Конкретный замедлившийся внутренний этап исходного инцидента пока не установлен.

## Проверки выпуска

| Требование | Проверка |
| --- | --- |
| Воспроизведение прежней гонки | Настоящий ограниченный обработчик пропущен; первый запрос отклонён, после завершения потока появляется поздний `ready` |
| Подготовка дольше срока наблюдающего обработчика | Быстрый обработчик сохраняет вход; медленная сборка выполняется на пути запроса; настоящий Admission разрешает результат |
| Отсутствие повторной сборки на каждом API-вызове | Два допуска одного хода, один вызов начальной подготовки |
| Необходимая зависимость недоступна | Отказ без вызова модели и без автоматического повторения подготовки |
| Технический срок подготовки превышен | Точный допуск получает `failed`; модельный путь закрыт |
| Продолжение того же сеанса | Два последовательных хода сохраняют сеанс, проект, задачу и рабочие сведения |
| Подмена или устаревший ход | Отказ до заимствования чужого допуска |
| Конкурирующая замена | Новый вход не подменяет работающую подготовку |

Нативные испытания используют настоящие интерфейсы Hermes и Admission; конечный провайдер в этих проверках не вызывается. Отдельные действительные модельные, установочные и рабочие проверки фиксируются в операторских квитанциях, а не выводятся из этой таблицы.

## Выпуск и откат

Изменение входит в цельный подписанный выпуск платформы. Wheel Intake содержит ту же исходную реализацию; два независимых локальных построения должны давать одинаковые байты. Все документы и закрепления описывают пару Memory 2.0.0-dev.48 + Intake 0.14.8.

Для обновления существующего экземпляра используется `packaging/upgrade_existing.py install` с точным корнем, новым каталогом резерва, полномочием оператора и цельным проверенным выпуском. Поддерживаемые исходные пары: dev.45/Intake 0.14.4 и dev.48/Intake 0.14.7. Сначала проверяется отдельная среда. Шлюз рабочего профиля штатно останавливается только после завершения его активных ходов.

Резерв сохраняет настройки, программы, подписанную регистрацию и согласованную копию памяти. Для отката команда `rollback` возвращает прежние программы и настройки; текущую базу, неизвестные исходы и расходы не возвращает в прошлое. Старые программы и резерв не удаляются.

# Identity 0.2.0 для разработки Hermes BNN

Протокол развивает наблюдающее хранилище 0.1.0. Исходный архив сохранён. Новое состояние — отдельная SQLite в `Identity/authority/state-v2`; память исследований хранится отдельно. Инициализация сохраняет существующие профильные SOUL.md побайтово и помечает их наблюдённой совместимой основой, без одобрения владельцем. Семь глубинных разделов остаются `null`.

Текущая библиотека реализует предложения, подписанное принятие, применение и отмену редакций, журнал восстановления и неизменные представления сессий. Подпись подтверждает владение местным ключом. Защита от неограниченной программы того же системного пользователя полностью не принята; такой путь исполнения в BNN закрыт. Права файлов сами по себе не доказывают изоляцию.

## Чтение состояния

```sh
cd '/Volumes/AgentRuntime2/active-runtime/Hermes BNN Releases/W4-20261026/Hermes-BNN-GSD-UDR-W4-neutral/Hermes'
bin/identity-bnn status
bin/identity-bnn verify
```

`archive_valid` относится к сохранённым редакциям и цепочке событий. Смотрите также состояние каждого профиля и `pending`: действующая область может быть заблокирована дрейфом или незавершённым применением. Чтение состояния не принимает и не применяет личность.

## Изменение по отдельному решению владельца

В текущей разработке реальное содержимое SOUL.md не меняется. Следующая последовательность — интерфейс для будущего отдельного решения и для изолированных синтетических испытаний. `ID-OLD`, `ID-NEW`, `SHA-OLD` и `SHA-NEW` заменяются фактическими значениями; не передавайте ключ подписи модели или в чат.

1. Подготовьте и прочитайте отдельный файл согласованного содержания. Зафиксируйте старую редакцию и `source_sha256` из `status`.
2. Создайте предложение:

```sh
bin/identity-bnn propose --profile main --source '/путь/к/согласованному.md' \
  --expected-revision ID-OLD --reason 'Причина согласованного изменения'
```

Команда возвращает `ID-NEW` и `source_sha256` (`SHA-NEW`). Файл профиля ещё не изменён.

3. После проверки содержания сформируйте и примените решение о принятии. Файл квитанции должен быть новым:

```sh
bin/identity-bnn sign --decision accept --revision ID-NEW --reviewed-sha256 SHA-NEW \
  --reason 'Проверено владельцем' --output '/путь/к/новой-квитанции-принятия.json'
bin/identity-bnn accept --receipt '/путь/к/новой-квитанции-принятия.json'
```

4. Отдельно разрешите применение к ожидаемому текущему состоянию:

```sh
bin/identity-bnn sign --decision apply --revision ID-NEW --reviewed-sha256 SHA-NEW \
  --expected-revision ID-OLD --expected-sha256 SHA-OLD \
  --reason 'Применить к указанному профилю' --output '/путь/к/новой-квитанции-применения.json'
bin/identity-bnn apply --receipt '/путь/к/новой-квитанции-применения.json'
```

Применение атомарно заменяет один выбранный SOUL.md. Старая редакция сохраняется. Незавершённое согласование файла с указателем фиксируется журналом и блокирует зависимые действия до восстановления. Дрейф не перезаписывается молча. Подписанную квитанцию нельзя повторно использовать после отката.

Новые сессии получают текущую редакцию. Уже закреплённая сессия сохраняет свою редакцию, включая перестроение системного сообщения при сжатии. Отмена исторической редакции блокирует её дальнейшее использование без подстановки другой личности. Текущую редакцию сначала нужно явно заменить.

## Откат, отмена и восстановление

Для возврата к прежней **принятой** редакции создайте новую квитанцию `sign --decision rollback`, указав целевую старую редакцию, её проверенный хеш и ожидаемые текущие редакцию/хеш. Примените её командой `apply --receipt`. Наблюдённая редакция не становится принятой автоматически. Другие профили, задачи, расходы, свидетельства и общая память не очищаются.

Для отмены неактивной редакции сформируйте квитанцию `sign --decision cancel` и передайте её `cancel --receipt`. История остаётся доступна владельцу; работа с отменённым представлением закрывается.

После прерывания посмотрите `status → pending`, затем:

```sh
bin/identity-bnn recover --intent IA-ИДЕНТИФИКАТОР
```

Если файл уже совпадает с одобренной новой редакцией, завершится указатель. Если сохранился старый файл, намерение будет отменено до замены. Третье неизвестное содержание требует отдельного разбора: команда его не перезаписывает.

## Другой владелец

`export-template --source '/путь/к/отобранному-шаблону.md' --destination '/новая/папка'` выгружает только явно отобранный файл и новый идентификатор экземпляра. История, ключ подписи и сессии не переносятся. Команда не определяет автоматически, свободен ли выбранный текст от личных сведений. Новая установка создаёт собственный ключ при инициализации; перенос текущей частной базы другим владельцам недопустим.

## Проверенные границы

Нативное устойчивое представление связано с экземпляром, профилем, сеансом, редакцией, построителем и хешем доставки. Вспомогательные операции и контрольные точки сохраняют ссылку на ту же редакцию. Ребёнок получает штатную базовую идентичность Hermes и техническое назначение той же линии происхождения; родительский SOUL и архив отношений ему не передаются. Идентичность не выдаёт прав на действия.

Каталог Identity исключён из обычных поисковых/читаемых проектов. Поставщик времени исполнения не загружает закрытый ключ подписи. Полная изоляция от неограниченного терминала остаётся открытым требованием; включать такой путь до её приёмки нельзя. Производственные BN и UDR этой разработкой не переключаются.
